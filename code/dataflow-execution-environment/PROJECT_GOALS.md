# PROJECT GOALS - Dataflow Language Compiler & Runtime

## Mission Statement

Implement a **compiler and runtime** for a dataflow programming language designed for children aged 6-9 years. The language processes JSON representations of tangible block programs (generated by external Computer Vision systems) and executes them using demand-driven evaluation semantics (Lucid model).

**Scope:** 
- ✅ Compiler (parser, validator, type checker)
- ✅ Runtime (demand-driven evaluator)
- ✅ Integration interfaces (LSP for IDE, HTTP API for CV system)

**Out of Scope:**
- ❌ Computer Vision system (external - generates JSON input)
- ❌ IDE/AR visualization (external - consumes runtime output via API)
- ❌ Physical block detection (external)
- ❌ Gesture recognition (external)

**Integration Points:**
```
CV System → JSON → [Compiler → Runtime] → Results → IDE/AR
                    ^^^^^^^^^^^^^^^^^^^
                    This is what we build
```

## Primary Objectives

### 1. Correct Dataflow Semantics
**Goal:** Implement authentic demand-driven evaluation based on Lucid.

**Success Metrics:**
- Runtime evaluates nodes only when demanded (verified by cache hit counts)
- Temporal operators work correctly (FBY counter: 0,1,2,3,4...)
- Parallelism emerges from independent demands (measured by concurrent evaluations)

**Non-Negotiable:**
- Demand-driven evaluation (NOT data-driven pipeline)
- Temporal operators via pure functions + cache (NOT mutable state)
- DAG validation (no cycles allowed)
- Type safety (compile-time type checking)

**Negotiable:**
- Choice of TypeScript vs other strongly-typed languages
- Specific cache implementation (LRU, Map, etc.)
- Use of Workers for CPU parallelism (Promise.all sufficient for MVP)

---

### 2. Language Completeness
**Goal:** Support all curriculum-aligned types and operations from specification.

**Success Metrics:**
- All 40+ operations implemented with correct semantics
- All 10 data types supported (Natural, Integer, Shape, Car, Food, Animal, Person, etc.)
- Type system prevents invalid programs at compile-time

**Non-Negotiable:**
- Types are integrated in language (not user-extensible)
- Operations match educational curriculum (geometry, counting, sets)
- Complete operation registry with type signatures

**Negotiable:**
- Order of implementing types (can prioritize most educational first)
- Number of operations in MVP (can start with 10-15, expand to 40+)
- Exact validation error messages (but must be clear)

---

### 3. Integration Capability
**Goal:** Provide clean interfaces for CV system and IDE to integrate.

**Success Metrics:**
- JSON input schema clearly documented and validated
- HTTP API for batch compilation/execution (CV system use case)
- WebSocket server for live validation feedback (IDE use case)
- Incremental runtime for REPL-like evaluation during construction
- Clear separation of concerns (Compiler ↔ Runtime ↔ Integration)

**Non-Negotiable:**
- Accepts JSON input (CV system output format)
- Provides structured output (results + execution trace for AR)
- Stateless core (Compiler/Runtime have no session state)
- Real-time feedback capability (for live construction)

**Negotiable:**
- HTTP vs other sync protocol for batch mode
- WebSocket vs SSE for live updates
- Custom protocol vs GLSP (graphical LSP - too green/heavy)
- ~~LSP~~ (wrong fit - designed for text, not graphs)

---

### 4. Performance for Educational Context
**Goal:** Reasonable performance for classroom use (5 children per session).

**Success Metrics:**
- Compilation <100ms for programs with <100 nodes (p95)
- Evaluation <10ms for programs with <50 nodes (p95)
- Can handle 5 concurrent compilation/execution requests

**Non-Negotiable:**
- Single-process architecture for simplicity
- Reasonable performance for educational context

**Negotiable:**
- Exact latency targets (can be 100-200ms if acceptable)
- Hardware requirements (can require decent machines)
- Scalability beyond 30 users (not needed for MVP)

## Implementation Strategy: Ralph Wiggum Method

### Principle
Build in **functional layers**, each completely working before moving to the next.

### Layer Sequence (Non-Negotiable Order)
1. **Layer 1:** Natural numbers + ADD only
   - Foundation: DataSource, Transformation, Output nodes
   - Compiler: JSON parser, DAG validator
   - Runtime: Demand-driven evaluator with cache
   - Tests: "3 + 2 = 5"

2. **Layer 2:** + Arithmetic operations (SUBTRACT, MULTIPLY, DIVIDE, COMPARE)
   - Layer 1 tests must still pass
   - Tests: complex expressions like "(3 + 2) * (10 - 6)"

3. **Layer 3:** + Curriculum types (Shape, Car)
   - Basic comparison operations
   - Tests: compare shapes by color

4. **Layer 4:** + Set operations (FILTER, UNION, INTERSECTION, etc.)
   - Tests: filter red shapes from mixed set

5. **Layer 5:** + Temporal operators (FBY, NEXT)
   - Demand-driven evaluation with time parameter
   - Tests: counter 0,1,2,3,4

6. **Layer 6:** + Streams (continuous data)
   - Tests: stream of sensor events

7. **Layer 7:** + Integration interfaces
   - HTTP API (batch mode for CV system)
   - WebSocket server (live validation for IDE)
   - Incremental Runtime (REPL-like evaluation)
   - Tests: external systems can compile/execute programs

### Why This Order? (Rationale for Negotiation)
- **Complexity:** Each layer adds ONE new concept
- **Dependencies:** Later layers depend on earlier ones working
- **Verification:** Easy to isolate where things break
- **Value:** Early layers demonstrate core functionality

**Negotiable:** 
- Can swap Layer 3 ↔ Layer 4 if curriculum types prove harder
- Can implement parts of Layer 7 early for incremental integration
- Can add sub-layers (e.g., Layer 2a: SUBTRACT only)

**Non-Negotiable:**
- Layer 1 must be first (foundation)
- Layer 5 must come before Layer 6 (streams need temporal operators)
- Never skip a layer
- Each layer must be complete and tested before moving on

## Acceptance Criteria Framework

### Format (Non-Negotiable)
Every feature spec must include:
```markdown
## Acceptance Criteria: [Feature Name]

### Behavioral Outcomes
- ✓ Observable behavior (WHAT system does)

### Observable Results  
- Input X → Output Y (concrete examples)

### Performance Requirements
- Latency < Nms

### Edge Cases
- Case → Expected behavior
```

### Derivation to Tests (Non-Negotiable)
Each acceptance criterion maps to ≥1 test in IMPLEMENTATION_PLAN.md

**Example:**
```markdown
## Feature: FILTER_BY_COLOR

### From Acceptance Criteria (specs/LANGUAGE_SPEC.md):
- ✓ Returns new set containing only matching color items
- ✓ Original set remains unmodified
- ✓ Performance <5ms for 100 elements

### Required Tests:
- [ ] Test: Filters red items from mixed set
- [ ] Test: Returns empty set when no matches
- [ ] Test: Original set unchanged (immutability)
- [ ] Benchmark: <5ms for 100 elements
```

**Negotiable:**
- Exact wording of acceptance criteria
- Number of edge cases (can prioritize most critical)
- Performance thresholds (can relax if justified)

**Non-Negotiable:**
- Must have acceptance criteria before implementing
- Tests must verify acceptance criteria (no "fake" tests)
- Can't claim feature complete without all tests passing

## Negotiation Protocol for LLM Planner

### When to Ask User for Clarification

**ALWAYS ask when:**
1. Specs missing acceptance criteria or contradictory
2. Multiple valid technical approaches exist (e.g., cache implementation)
3. Performance targets unclear or unrealistic
4. Layer order seems suboptimal for specific reason
5. Integration interface design requires user decision

**Example questions:**
- "Spec doesn't define UNION behavior for empty sets. Return empty set or error?"
- "Performance target <1ms per node difficult with complex operations. Relax to <5ms?"
- "Layer 3 requires Shape type (complex). Swap with Layer 4 (simpler sets first)?"
- "LSP vs custom protocol for IDE? LSP = more standard, custom = simpler/faster"

### How to Propose Alternatives

**Format:**
```markdown
## Proposed Alternative: [Topic]

### Current Plan
- What specs/plan says

### Issue
- Why this might be problematic

### Alternative
- Proposed different approach

### Tradeoffs
- Pros: ...
- Cons: ...

### Recommendation
- Suggested course of action + rationale
```

User ALWAYS has final say on:
- Technical architecture decisions when multiple valid approaches exist
- Performance/completeness tradeoffs
- Integration protocol choices (LSP, HTTP, WebSocket)

Planner should **challenge** unclear requirements but **defer** to user decisions.

## Key Constraints & Tradeoffs

### Correctness vs Ease of Implementation
**Constraint:** Dataflow semantics are subtle (demand-driven, temporal operators)
**Tradeoff:** Strict correctness (complex) vs permissive (easier but wrong)
**Decision:** Strict correctness - this is a learning tool, must be semantically correct

### Performance vs Simplicity
**Constraint:** Must handle 30 concurrent users
**Tradeoff:** Simple architecture (single-process) vs complex (multi-process)
**Decision:** Simple for MVP, optimize if profiling shows bottlenecks

### Completeness vs Time
**Constraint:** 40+ operations is many to implement
**Tradeoff:** All operations (complete) vs subset (faster)
**Decision:** Incremental - start with 10-15 most educational, expand via layers

## Open Questions for User

When planning begins, planner should ask:

1. **Priority Operations:** Which 10-15 operations are most critical for MVP?
   - Arithmetic (ADD, SUBTRACT, MULTIPLY)
   - Comparison (COMPARE_BY_COLOR, COMPARE_BY_SIZE)
   - Filtering (FILTER_BY_COLOR, FILTER_BY_TYPE)
   - Sets (UNION, INTERSECTION)

2. **Integration Protocol:** Preference for IDE integration?
   - Custom WebSocket (simple, tailored, real-time)
   - GLSP (graphical LSP - standard but green/heavy)
   - ~~LSP~~ (designed for text languages, poor fit for graphs)
   - Direct library usage (no protocol, just import)

3. **Execution Modes:** Which evaluation modes are critical?
   - Batch mode (complete program → results) - for CV system
   - Incremental mode (partial graph → partial results) - for live construction
   - Both?

4. **Execution Trace Detail:** How much execution info for AR visualization?
   - Minimal (just final results)
   - Medium (node-by-node state)
   - Detailed (every evaluation step, cache hits/misses)

4. **Error Handling:** When program has errors...
   - Fail compilation with detailed error messages
   - Best-effort execution with warnings
   - Hybrid (hard errors vs soft warnings)

5. **Performance Targets:** Acceptable latencies?
   - Compilation: <50ms? <100ms? <200ms?
   - Execution: <10ms? <50ms? <100ms?
